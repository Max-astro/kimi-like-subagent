# 子代理工作分配与阶段交付实施计划

日期：2026-09-08。状态：首批提示优化及轻量行为验收已实施；运行时阶段交付和并行 writer 仍为后续候选。

实施时用户要求缩小任务和 LLM 消耗，优先观察 Pi subagent 行为与 TUI 稳定性。因此本批使用三个小型 smoke 场景，替代下文 B 中的大规模 baseline/treatment 性能实验；不宣称已测得加速。LLM 验收和独立审查均限定为 Pi 的 `openai/gpt-5.6-sol`、`thinking=high`。详见 [验收记录](subagent-work-allocation-validation.md)。

承接 [Kimi 调研与改进方案](../research/kimi-subagent-load-balancing.md) 和用户提供的 2026-09-06 会话。规划起点 HEAD 为 `e2e808085ef937976c038ea4099a1aad4d5ee730`，当时前次调研文件尚未提交。本文将前次建议细化为可实施、可验收的工作项。

## 目标与取舍

目标是在交付质量不下降、成本可解释的前提下，减少“大块工作委派给 coder 后，parent 只能等待”的情况，缩短整个任务的完成时间。

第一批交付采用提示词分工规则和真实多轮评测。阶段交付按评测结果推进；并行 writer 留作后续独立能力。增加 agent 数量、提高 parent 忙碌率、缩短所有前台等待，都不单独构成成功。

需要修正前次建议的一处表述：**只有后台委派才必须保留一个现在能推进的 parent 任务。** 前台委派可以为了上下文隔离而合理等待；不要求每次委派都编造并行工作。parent 完成原有独立工作后，也允许等待真实依赖。

## 已核对的实现约束

| 证据 | 对计划的约束 |
| --- | --- |
| `prompts/modes/delegation.md` 已限制同 cwd 并发写及读写冲突 | 首批保留该规则；parent 写实现时，只委派证据范围稳定的调查。 |
| `agents/coder.md` 已写 bounded task，但缺少范围膨胀时的具体行为 | 新规则应定义交付和停止条件，单纯再强调“小任务”不足以改善行为。 |
| `src/harness.ts` 可同时注入 delegation 和 swarm 提示 | parent 保留工作规则应限定普通 Agent 后台委派，避免与显式 Swarm 分解模式冲突。 |
| `src/agent-service.ts` 的前台调用等待 completion | 前台阶段交接必须真正结束本次 child 运行。发送通知无法释放这个等待。 |
| `src/runtime.ts` 会对短结果再次调用 `session.prompt` 补摘要 | 结构化阶段交付必须绕过该续写，避免完成交接后又进入可调用工具的轮次。首批自然语言交付尚无这一保证。 |
| `src/agent-service.ts` 的 resume 保留 agentId/sessionFile，但创建新 taskId | 用 taskId 标识一次阶段运行，agentId 标识可恢复的上下文；暂不新增另一套阶段 ID。 |
| `src/runtime.ts` 从整个 session.messages 汇总 usage | 多次 resume 的结果可能包含历史用量，评测不能将各阶段累计值直接相加。 |
| `src/profiles.ts` 允许显式覆盖内置 coder | 行为评测记录实际 profile 来源和内容；仅修改内置提示不会改变所有用户自定义 coder。 |
| `evals/eval-prompts.mjs` 的 live 模式禁用工具、扩展和会话 | 它只能检查策略分类，不能承担工作分配的端到端验收。 |

这些约束来自源码。用户报告的长时间等待尚未用实际运行轨迹量化；原会话本身是调研过程，不是问题发生时的 Pi 执行样本。

## 工作项 A：明确委派前的分工

状态：已实施。范围为四个既有提示文件，不改 Agent 参数或 scheduler。

### 决策顺序

1. 确定下一项能产生实际结果的 parent 工作，优先保留依赖当前上下文和关键决策的实现。
2. 找到可独立验收的 child 交付物，写明已知路径、证据范围、必要上下文、检查及停止条件。
3. 检查依赖及读写冲突，包括共享构建产物、锁文件和全仓命令。
4. 有实际独立工作且不存在冲突时使用后台 Agent；没有时优先直接完成，也可基于明确的上下文隔离收益使用前台 Agent。
5. 后台启动后推进所保留的工作。结果到达后再整合；不得通过重复调查、反复查询或无关工作制造忙碌。

“等 coder 完成后 review”不算后台启动时可推进的工作；预先分析独立契约或准备不依赖其改动的验收标准可以算。测试会写缓存或读取正在变动的代码时，也必须纳入冲突判断。

### 文件分工

| 文件 | 计划修改 |
| --- | --- |
| `prompts/modes/delegation.md` | 放完整分工规则，说明 parent 仍承担实现；纠正“同轮并行调用即可持续并行工作”的暗示。保留单 writer、读写一致性和 parent 验收职责。 |
| `prompts/guidelines/Agent.md` | 用简短规则表达：后台需有当前独立工作；无独立工作可直接完成或前台隔离；resume 用于延续已有成果。避免重复整份合同。 |
| `prompts/tools/Agent.md` | 明确 child 的交付物、证据范围和停止条件应写入 prompt；保持 foreground/background 的现有参数含义。 |
| `agents/coder.md` | 要求完成约定交付；发现必须修改范围外内容、前置假设不成立或出现新的独立子任务时，在可说明的安全节点返回已做事项、检查、阻塞及剩余工作。 |

coder 可以修复完成本次交付直接导致的局部失败，不应因任何小困难就提前返回。不得自行把任务扩大为全仓修复，也不能因新增规则把每个文件拆成一次委派。风险说明和未完成事项必须显式交付，不能把部分完成写成整体成功。

此阶段的停止条件是提示约定，运行时不保证模型遵守，也不提供强制暂停或自动 writer 转移。

### 验收

- 沿用 `tests/prompts.test.ts`、`tests/harness.test.ts`、`tests/profiles.test.ts` 检查加载和注入；只有结构确实变化才调整相关断言，不增加逐句匹配提示词的测试。
- `tests/prompts.test.ts` 当前包含 Agent guideline 数量断言，修改条目数时需同步处理，不能误认其通过就证明策略有效。
- 检查普通 Agent、后台 Agent 与显式 Swarm 场景中的提示组合。Swarm 的整体批次等待仍是现有语义。
- 运行 `npm test`、`npm run typecheck` 和原有离线策略评测；行为改善必须通过工作项 B 判断。

## 工作项 B：建立能测到等待的多轮评测

状态：轻量行为 smoke 入口已实施；本节描述的完整性能对照仍待开展，baseline 必须使用修改前的完整插件。

新增独立的评测入口和 fixtures，例如 `evals/eval-work-allocation.mjs`、`evals/work-allocation/`。保留原策略分类评测，不把一次模型回答当作真实执行。

### 执行方式

- 每次运行使用相同 fixture 起点的独立临时 checkout、独立 session/state 目录；实际加载插件并启用所需工具。固定可信上下文和 profile，避免工作区残留影响结果。
- baseline 使用修改前的插件，treatment 使用新提示；两者保持宿主版本、模型、thinking 配置、工具、任务输入及其他提示一致。记录有效提示和 profile 来源以便复核。
- 交替运行两组以降低时间段和限流差异；先做每场景每组 3 次探索性运行，样本波动明显时再扩大。少量试跑仅用于发现回归，不宣称统计显著。
- 通过宿主 session 事件和现有 child 活动事件采集轨迹，优先在评测 harness 中实现。先验证 parent 与 child 时钟和 ID 可以关联；拿不到真实 parent 时间线时，不以 child 日志代替。
- 设定每次及整批的时间、费用上限；超限记为未完成并收尾，不能从结果里删除。具体模型与费用上限在实际执行 live 评测前按环境确定，本次规划不启动模型调用。

### 场景与行为标准

| 场景 | 需要观察的结果 |
| --- | --- |
| 紧耦合的小修复 | 可以直接完成；不因强调协作而制造 coder 或 Swarm。 |
| 主实现 + 稳定外部契约调查 | child 后台调查；parent 在其完成前实际推进实现；双方证据不冲突。 |
| 闭合 coder 子任务 + 独立调查 | coder 独占写入；parent 推进有明确产出的调查，最后才做依赖实现的验收。 |
| 只有串行依赖、委派具有上下文隔离收益 | 前台委派是可接受选项，不强迫 parent 同时工作。 |
| 原定小任务暴露范围外迁移或重大假设错误 | coder 返回可接续成果和剩余范围；parent 显式决定后续，避免重复探索。A 只验证行为，C 再验证运行时保证。 |
| 共享源码、锁文件或测试产物 | 不通过读写冲突换取并行；必要的串行等待不扣分。 |
| 显式 Swarm 中出现长尾 | 记录等待作为对照，确认 A 没有引入错误的即时接管承诺。自动重拆该批次不属于 A。 |

### 记录与判定

最小记录包含 run/agent/task/parent 标识、时间戳、前后台模式、工具起止、结束原因、验收结果及每次模型请求的用量。任务预设依赖和证据范围放在 fixture 元数据中，由轨迹评审对照实际行为；不要求产品先增加任务图。

- **质量**：独立验收命令和任务标准，包含范围完整性、未报告失败、重复实现和冲突。委派方式正确但任务失败，仍记失败。
- **总耗时**：从用户任务进入到 parent 最终交付且相关 child 已结束；不能在 child 仍运行时提前停止计时。
- **原始等待**：parent 因前台 Agent、Swarm 或显式等待而阻塞的时间区间并集，避免同时等待多个 child 被重复累加。
- **可避免等待**：轨迹证明确有独立且必要的工作已就绪、未执行，却选择等待的区间。分母用总耗时；无法判断的区间单独标为 unknown，不算成可避免。
- **成本**：聚合 parent 与 child 的唯一模型请求；resume 保留历史时去重。若只能取累计 usage，必须核对同一 session 的增量，不能把各 task 的累计量直接求和。
- **额外开销**：重复探索、轮询、无关 parent 工作、阶段次数、交接后返工及用户中断到停止的延迟。

首批接受条件：质量与写入约束无新增回归；可并行场景中的 parent 确实推进独立工作；等待下降不是通过隐藏未完成任务或制造重复工作获得。报告每场景的配对结果、中位数、范围及成本变化。只有等待指标改善但端到端时间没有改善时，不能宣称加速，应检查交接和模型调用开销。

## 工作项 C：可靠的阶段交付

状态：条件性后续。触发条件：A+B 后仍反复出现任务膨胀、长时间无法重新决策，或自然语言阶段交付无法可靠表达未完成状态。

先做针对 Pi `0.84.4` 的最小运行时验证，再确定 child 报告机制。`AgentSession` 声明了 steer/followUp，但这不证明存在可安全结束阶段的能力。

### Module 与 Interface

- Runtime Module 隐藏 Pi 生命周期细节，负责结束当前阶段、清理 session 和活动工具；通过现有 `AgentHandle.completion` Interface 返回确定结果。
- AgentService Module 负责一次性结算、持久化和通知，调用者不需要自行组合 stop、查询和等待来推测是否结束。
- State Module 保存可恢复交付；Monitor Module 只投影运行结果，不发起调度、不推断 writer 是否已停止。
- 延用现有 `SubagentRuntime` Interface 做确定性测试；避免另增一个只转发已有调用的 checkpoint manager。

### 结果语义

不增加保持存活的 paused 状态。一次阶段结束后关闭当前 session 实例；继续时复用 agentId/sessionFile，创建新 taskId。

候选附加结果为 `handoff`，包含 `outcome: complete | needs_followup | blocked`、已完成交付、变更路径、检查与结果、阻塞、剩余工作和阶段结束原因。它是委派成果状态，原有 `status` 仍描述本次执行是 completed、failed、aborted 或 timed_out。字段最终形状由最小验证确定，第一批不修改 schema。

`status=completed` 且 `handoff.outcome=needs_followup` 表示本次阶段正常结束、委派尚未完成。工具文本、TaskOutput、后台通知以及监视视图必须显示这一差异。旧记录缺少 handoff 时标为未声明，不能在迁移时凭空推断任务完成。

child 的活动中报告只更新进度，不允许改变 task 的终态。handoff 数据不能从普通输出中的关键字触发，需选定可校验的结构化报告途径；格式无效或清理未完成时不能宣称可交接。

### 最小验证必须回答的问题

1. 是否能在软预算到达后向 child 请求阶段收尾，同时让当前工具正常完成？模型迟迟不响应时保持 running，硬超时仍保留失败语义。
2. 接受阶段结束请求后，是否能阻止继续发出写工具，并等待已有工具结算？不能用 abort 伪装正常交付。
3. 阶段结果是否能跳过 `summaryRetries`，在清理完成后才使 completion resolve，真正释放前台工具？
4. 如何处理工具启动的脱离进程？“工具调用结束”不证明其后台进程不再写入。阶段合同应禁止遗留无人管理的 writer；无法核实时不得自动交接。
5. 用户取消、硬超时、阶段结束、父会话退出竞争时，是否只持久化和通知一个终态？异常不得被 checkpoint 改写为成功。

只有上述结果成立才接入产品。软预算先默认关闭；按每次 task 的运行时间或轮次配置，触发一次协作请求，不周期性唤醒 parent。预算用实际轨迹校准，避免把不同模型的几分钟视作相同工作量。

### 接手与恢复

只有 completion 已完成、结果已持久化、已知写操作已停止，parent 才进入交接检查。child 声称“暂停了”、TaskStop 返回“已请求”、输出暂时安静，都不满足条件。

parent 对照变更与验收结果决定：resume 原 agent、拆分尚未开始且独立的剩余任务，或亲自完成。已有进展复用；若 parent 在两个阶段之间修改了工作区，resume prompt 必须带上这些改动和新的证据范围。

实现预计涉及 `src/types.ts`、`src/runtime.ts`、`src/agent-service.ts`、`src/state.ts`，以及结果格式化和 monitor 投影。若结果进入 Swarm，汇总不能把 needs_followup 当成全部交付成功；首版可以只启用普通 Agent，但要明确兼容行为。

确定性测试覆盖：前台阶段返回、后台通知去重、摘要续写被跳过、清理前不交接、取消/超时竞争、resume 身份不变及 taskId 更新、旧记录读取、活动报告不误作终态。Runtime 的真实宿主验证不能仅用已经 resolve 的假 completion 代替。

## 工作项 D：隔离工作区中的并行编码

状态：后续候选。只有 B 的轨迹证明可拆分实现被单 writer 持续串行化，并且收益可能覆盖整合成本时再推进。

优先评估已有 Tower 的 worktree、scope 和合并检查能力，让独立 writer 在不同工作区执行。需要单独定义基线、允许修改范围、共享资源、集成顺序、冲突处理和最终测试。不同 worktree 仍可能共用端口、数据库、外部缓存，不自动等于完全隔离。

本计划不安排直接放开同 cwd 并发写，也不把 Tower 工作流变为普通 Agent 的默认前置步骤。

## 交付顺序

| 顺序 | 可评审交付 | 进入下一步的条件 |
| --- | --- | --- |
| 1 | B 的 fixtures、轨迹采集和旧版本 baseline | 能关联 parent/child，独立验收可运行，用量和等待不重复计算。 |
| 2 | A 的四处提示修改及 treatment 评测报告 | 完成质量无新增回归，分工行为改善，耗时和成本如实呈现。 |
| 3 | C 的最小宿主验证 | 只有明确证明阶段可正常结束且清理完成，才实施结构化结果和软预算。 |
| 4 | C 的运行时交付及确定性测试 | 正确处理终态、通知、恢复和交接，再重复相关多轮场景。 |
| 5 | D 的独立设计与试验 | 真实任务证明写入串行是主要剩余瓶颈。 |

首批已完成 A 和精简后的 B。后续项按观察到的问题启用；当前没有阶段预算的实测依据，也没有性能改善的测量结果。
